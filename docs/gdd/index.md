# GDD 索引

这是通用骨架，不预设游戏类型。开工时先按游戏实际情况增删领域，再开始填写。规则见 [traceability](../traceability.md) §1。

## 领域

| 领域代码 | 文件 | 内容 |
| --- | --- | --- |
| `CORE` | [overview.md](overview.md) | 概念、设计支柱、核心循环、成功与失败、范围 |
| `CONTROL` | [controls.md](controls.md) | 平台、输入、摄像机或视角 |
| `MECH` | [mechanics.md](mechanics.md) | 玩家动词、核心规则、时间行为、反馈、容差，以及类型专属机制 |
| `CONTENT` | [content.md](content.md) | 内容清单、关卡、角色与对象、进度与难度 |
| `UI` | [ui.md](ui.md) | 界面流程、HUD |
| `ART` | [art.md](art.md) | 美术方向、调色板与参考 |
| `AUDIO` | [audio.md](audio.md) | 音效、音乐 |

- 领域代码是大写英文单词，会直接用进段落编号（`GDD-MECH-02`）。第一个段落被任务引用之后，就不要再改领域代码。
- 不需要的领域可以整个删掉，比如没有音乐的小游戏可以删 `audio.md`。需要新领域时在这张表里加一行，再建对应文件。

## 段落格式

```markdown
## GDD-<AREA>-<nn> 段落标题
revision: 1
status: draft
needed_by: M1

正文（可以用中文）。
```

- `status`：`draft`（草稿，可以指导原型，但不算已批准）、`approved`（只有你能设）、`retired`（废弃，保留标题并写明替代段落）。
- `needed_by`：哪个里程碑开工前必须批准。没写就表示没有硬性时间点。
- 含义改变时 `revision` 加 1；改错字不加。
- 编号永远不复用。新段落取该领域下一个没用过的号。上面的示例用了占位符，不是真实段落。

## 按里程碑要批准的段落

下表方便你查看，以各段落里的 `needed_by` 为准。lead 在每个里程碑开工前运行 `npm run gdd:check -- --milestone <Mn>`，列出还没批准的段落。

| 里程碑 | 骨架中标注的段落 |
| --- | --- |
| M1 | CORE-01 概念、CORE-03 核心循环、CORE-04 成功与失败、CONTROL-01 平台、CONTROL-02 输入、CONTROL-03 摄像机或视角、MECH-01 玩家动词、MECH-02 核心规则、MECH-03 时间行为、MECH-04 反馈、MECH-05 暂定容差 |
| M2 | CORE-02 设计支柱、CORE-05 范围与不做的事、CONTENT-02 关卡或场景、CONTENT-03 角色与对象、UI-01 界面流程、UI-02 HUD |
| M3 | CONTENT-01 内容清单、CONTENT-04 进度与难度、ART-01 美术方向、ART-02 调色板与参考、AUDIO-01 音效、AUDIO-02 音乐 |

## 加类型专属段落

确定类型后，把这个类型特有、而且会影响实现或测试的规则写成新的 `MECH` 段落，从 `MECH-06` 开始编号，并标上 `needed_by`。例如：

| 类型 | 可能要加的段落 |
| --- | --- |
| 动作 | 连招与输入缓冲、取消窗口、无敌帧、hitstop、受击反应 |
| 解谜 | 谜题元素与互动规则、提示规则、撤销与重置 |
| 卡牌或回合制 | 回合顺序、效果结算顺序、牌库与抽牌、随机性 |
| 平台跳跃 | 跳跃手感（土狼时间、跳跃缓冲）、碰撞容差、检查点 |
| 节奏 | 判定窗口、音画同步与延迟校准 |
| 模拟经营或放置 | 资源与产出、经济平衡、离线进度 |

这张表只是提示，不是要求。每条规则都要写到 tester 能据此写测试的程度：在什么条件下、发生什么、数值范围是多少。
